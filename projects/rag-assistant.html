RAG AI Research Assistant

Retrieval-Augmented Generation • Pinecone & Cross-Encoder Reranking • FastAPI & Docker

The Objective

Building a containerized RAG system that answers questions strictly from a user's own research papers - and refuses to answer when it can't.

Most RAG demos stop at "it retrieves and it answers." This project treats grounding as a first-class requirement: a FastAPI backend ingests PDFs, embeds and reranks retrieved chunks before they ever reach the LLM, and hard-refuses to answer when nothing relevant is found - rather than letting the model quietly fall back on its own pretrained knowledge. The system evolved from a local ChromaDB prototype into a Dockerized service backed by Pinecone, with per-document ingestion and deletion managed entirely through the UI.

A query answered by synthesizing across multiple reranked chunks, with per-chunk file, page, and snippet citations shown alongside the answer.

Stack

FastAPI, LangChain, Ollama (Llama 3, nomic-embed-text), Pinecone, BGE Cross-Encoder Reranker, Streamlit, Docker & Docker Compose.

Technical Gems

  • • Hard grounding guard: if reranked retrieval returns nothing relevant, the API returns a fixed refusal without ever calling the LLM - removing the model's ability to hallucinate from pretrained knowledge.
  • • Reranked retrieval: top-20 similarity candidates from Pinecone are re-scored by a BGE cross-encoder down to the 5 most relevant chunks per query.
  • • Per-document lifecycle: ingestion tracks each chunk's Pinecone vector ID, enabling clean per-file deletion on a serverless index that only supports delete-by-ID, not delete-by-filter.

Grounding Over Fluency

The core engineering problem wasn't getting an LLM to answer questions - it was stopping it from answering confidently when it shouldn't. Early iterations let the retrieval pipeline hand the model whatever chunks it found, however weak, and trusted the prompt to enforce refusal. In practice, an instruction-following model like Llama 3 doesn't reliably self-police that boundary. The fix moved the guard into code: if the reranked retriever returns zero relevant chunks, the API returns a fixed response and skips the LLM call entirely, so refusal is a deterministic branch rather than a prompt suggestion.

From ChromaDB to Pinecone

The project began as a local script backed by ChromaDB. Moving to a cloud-hosted, serverless Pinecone index decoupled the vector store from any single machine, but surfaced a real constraint: serverless Pinecone indexes support delete-by-ID only, not delete-by-metadata-filter. Ingestion was restructured to assign and persist a deterministic vector ID per chunk, so any document can later be cleanly removed - vectors and all - without wiping the whole index.

"A RAG system is only as trustworthy as its refusals. Answering confidently from the wrong source - or from no source at all - is a worse failure than saying 'I don't know.'"

Containerized, Reranked Retrieval

The FastAPI backend, retrieval pipeline, and reranker run inside Docker for consistent deployment. On ingestion, PDFs are chunked with a recursive character splitter and embedded via Ollama's nomic-embed-text. On query, Pinecone's top-20 similarity results are passed through a BGE cross-encoder to rerank down to the 5 most relevant chunks before Llama 3 synthesizes an answer - trading a small amount of latency for materially better precision than similarity search alone.
